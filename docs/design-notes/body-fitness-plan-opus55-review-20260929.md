## 総合判定

計画冒頭の方針（計画:5,9,11）は妥当です。ただし本文の工程と次手が旧順序のままなので、再出発の指針としてはこのままでは使えません（阻害1件）。

出生遅延は速度改善では解けません。bit一致を保ったtime4版でも、固定690表1件のCPU時間は約7.5秒です（time4結果:11-14）。演奏上の加入タイミングとは桁が違います。問題は計算方式ではなく、72 frame oracleを出生要求の**後**に置いた構造にあります。候補身体密度は環境に依存しません（準備:6-9）。したがって参照と同じ関数を要求**前**へ移せば、数値を変えずに解ける可能性が高いと考えます。

本番方式の最有力は次の方式です。
- 子の身体を要求前に確定する。
- その候補密度表を事前準備して在庫化する。
- 出生時刻には、最新の環境・占有・親energyで採点・抽選・commitだけを行う。

ただし成立条件（Recipe seedの決定時点、landscape依存mode pattern、child ID依存）は資料から確定できません。先に静的確認が要ります。

## 所見

**1. 阻害｜計画:205-215, 228-232, 267-270, 480, 682**
- 根拠：冒頭（9）は「全候補準備を出生要求後に置かず、前倒しする」としています。一方、末尾の最新次手（682）は「次の主課題は全690×72frameの計算費用」のままです。F3方針（230）は最適化を先頭に置き、§7（267-270）は09-26の最初の単位を指しています。
- 問題：末尾の節に従う読み手は、停止済みの性能探索へ戻ります。
- 最小修正：冒頭直後に「現行工程」節を新設し、以下の日付節は履歴だと明示します。682は削除せず、上位節で上書きした旨を記します。

**2. 重大｜出生登録:12-13,19／計画:11**
- 根拠：登録は、予約後にworkerが全bin表を準備する経路を本番配線としています。成功条件は配送・数値・資源だけで、遅延の上限はありません。
- 問題：参照計算（oracle）が本番のクリティカルパスに入っています。postrun-v2の36/36合格は登録どおり有効ですが、実用性については何も示していません。
- 最小修正：postrun合格は旧登録の結果として保持し、遡って不合格にもしません。実用受入は別契約とします。

**3. 重大｜計画:11**
- 根拠：「初期spawnとrespawnの許容遅延を別に明確化する」とあるだけです。
- 問題：出生種別、時計、計測点、超過時の動作がどれも決まっていません。
- 最小修正：第一作業の成果物に予算表を含めます（後述）。

**4. 重大｜出生登録:10,11,13**
- 根拠：現行の登録には次の4点があります。
  - (a) 子Recipeのseed frameを予約時に固定する。
  - (b) Landscape依存のmode patternをcommit前に照合する。
  - (c) 密度をchild IDに紐づける。
  - (d) 非遺伝templateでは親metadataが身体乱数に入らない。
- 問題：(d)は前倒しに有利です。しかし(a)(b)(c)の実装次第で、身体の前確定が乱数系列・身体分布・ID順の意味を変えます。
- 最小修正：実装前に静的確認します。意味が変わる場合は、変更点を明記した別登録とします。seedの時点を黙って動かしてはいけません。

**5. 重大｜計画:31／準備:9／dynamic-density結果:3**
- 根拠：先行提案は「準備共有・軽量身体表現・有界候補探索」を同格の比較対象にしています。しかし資料上、いずれも弱い候補です。
  - 共有：個体別Recipeで密度が違うため不採用済みです（計画:31）。Recipe hash一致時のcache（計画:440）の特殊例にすぎません。
  - 軽量表現：密度補間は全30組が不合格で、peak配置の離散切替に弱いことが示されています。
  - 有界探索：旧Cで上位候補を選ぶ前段は棄却済みで（準備:9）、候補集合を変えるモデル変更です。
- 問題：三案の同格比較は、再び大規模な比較取得を招きます。後二者はoracleを別モデルで置き換えるため、F2比較と36条件の数値照合が無効になります。また、先行提案の「密度・score・順位・選択確率・energyの精度契約」は、モデルを変える場合にのみ必要です。
- 最小修正：三案とも主方式候補から外します。検討は、前倒しで解けない残余（所見6）に限ります。

**6. 重大｜出生登録:13／計画:656,678**
- 根拠：PeakBiasedの非ゼロ局所探索は、出生時の環境で選ばれたpeakに依存します。旧協調workerでは、追加1候補が28.824 ms、要求から出生まで3072 sampleでした。
- 問題：全表を前倒ししても、この追加密度は要求後の計算として残ります。
- 最小修正：出生遅延を「採点・抽選＋局所Hzのexact計算件数」として予算化し、優先slot（協調workerの交互順）で処理します。局所Hzを格子へ丸めることはしません。

**7. 軽微｜計画:3,13,29**
- 根拠：「実行中」（3）と「後検査を実行中」（29）は、postrun-v2（pass=true、SHA `92c6ab7b…`）より古い記述です。13の「30秒paced取得は行っていない」はruns/SIMD版についての記述ですが、33のtime4による3出生と並ぶため矛盾に読めます。
- 最小修正：postrunの結果とSHAを記載し、「登録上の合格」と「実用は未受入」を一文で区別します。

**8. 軽微｜計画:440／出生登録:9**
- 根拠：既存cacheの上限は1 MiB/sourceです。690候補×公開690 binのf32表は、算術で約1.8 MiBになり収まりません。
- 最小修正：在庫の保持量と補充CPUを、既存cache・4 source予算とは別枠で予算表に計上します。

## 参照と本番の区別

72 frame oracleは固定された評価モデルであり、物理的真理ではありません。その価値は「本番出力がこのモデルと一致するか」を判定できる点にあります。

前倒し方式は同じ関数を同じ入力で早く呼ぶだけなので、次の利点があります。
- 本番出力をbit一致で検証でき、既存の36条件checkerとoracle照合をそのまま流用できます。
- 失敗済みの登録（補間30組、peak前補間30点、u32/runs/SIMD）は、失敗のまま保持できます。

これが前倒し方式を推す主な理由です。

## 前倒し・共有の成立条件

| 観点 | 条件 |
|---|---|
| 個体差 | 表の単位はRecipe hash。共有はhashが一致するときだけ |
| source/seed | 身体乱数が予約frameに依存するなら、前倒しで身体が変わる。counter索引の専用系列なら、引出し順＝消費順で不変。**要静的確認** |
| 親決定時点 | 非遺伝では身体に親が入らないので、親抽選は出生時に残せる。F6で遺伝を入れると表が親依存になり前提が崩れる |
| 身体変更 | template・policy・space/fs/NSGTの変更で在庫を失効させる（出生登録:12,14の規則を流用） |
| landscape依存 | 該当するtemplateは前確定不可、またはcommit照合で失効。該当templateは**未確認** |
| 予告なし | template単位で「次の子」の表を在庫しておけば対応できる。在庫切れ時は遅延を記録して待つか、明示拒否する。点fallbackを成功と数えない（計画:235-236） |
| 環境・親energy・占有 | すべて出生hopで決定する（現行どおり） |

## 第一作業：身体前確定の静的確認と予算表の起草

読取のみで、コード変更と取得は行いません。

**入力**
- time4 job-probe treeの `src/life/community/async_birth.rs`、`respawn.rs`、`frequency.rs`、`src/life/body_footprint.rs`
- Recipe・template生成箇所と、scenarioのSpawn発行経路
- 出生登録、postrun-v2、on18-v1

**確認項目**
- Q1：子Recipeの乱数入力（seed frame・counter・child ID・親・landscape）と、その決定時点
- Q2：landscape依存のmode patternを持つtemplateの有無
- Q3：身体乱数系列が出生種別間で共有されているか
- Q4：respawnの遅延（約2.5秒）が初期出生より短い理由（候補数・範囲など）
- Q5：予定Spawnを再生前に列挙できるか
- Q6：局所探索の追加Hz件数の上限

**成果物**
- Q1〜Q6への回答（file:lineで根拠を示す）
- 計画の現行工程節の改訂案
- 予算表草案

**終了条件**：全項目に根拠付きの回答があること。根拠が見つからない項目は、理由を付けて「未確認」とします。

**中止条件**：全templateが出生時のlandscapeに依存する場合、または前確定が乱数系列の変更を避けられない場合です。このときは在庫実装へ進まず、意味変更の内容と推奨一案を示して止めます。

**決定の分担**

| 区分 | 内容 |
|---|---|
| 未決（作者判断、F5で試聴確定） | 許容遅延。**提案値**：予定出生は予定hopで出生（遅れ0 hop）、突発Spawnとrespawnは10 hop（約107 ms）以内 |
| 実装者が既存仕様から決められる | 失効key、単一worker、保持量の計上、scene開始前prefill（冷状態）、在庫切れ時の報告、ID割当をcommit時に行うこと（出生登録:10） |
| 実測値からの算術 | 補充は1表あたり約7.5 CPU秒。在庫の深さは死亡頻度に依存するが、その値が資料にないため未決 |

**担当**：Q1〜Q6の読取と文書整理はsol6で足ります。意味変更の判断と本番方式の確定はastraが扱ってください。
