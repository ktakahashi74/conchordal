## 1. 原則

規則の正本は `AGENTS.md` の Progress and Validation Scope と、設計台帳である。ここには要点だけを書く。

- **二層**：既存文献の定量モデルは、原典との対応を確認した部分だけを原理層とする。独自の近似、閾値、結合係数は作者規則層に置く。
- **受入**：原理層は、原典モデルとの数値照合、登録した因果差、宣言した負荷での実時間動作で受け入れる。
- **評価の要否**：評価（数値・主観とも）を置く前に、結果で変わる決定、原理や消費者や既存データで答えが出ない理由、選択肢を弁別できることを書く。変わる決定がなければ置かない。主観評価は、原理でも消費者でも決まらない自由パラメータの選定に使う。
- **提案で足りる**：個体は局所的な知覚と反応で動く。全候補の表や、聴く前の厳密な予測は、それを必要とする消費者がある場合だけ作る。
- **数値の由来**：許容差と負荷目標は、原理か、消費者の判断が変わる誤差か、宣言した対応範囲から導く。
- **消費者**：既定の演奏経路に消費者のない機構を、本体の必須にしない。

## 5. 進め方

- 体制（2026-10-07 の作者指示）：統括はClaude Opusのセッションが行う。workerは `gpt-6.1-sol` の `xhigh` で、KEIOアカウントのagent-shell bufferとして立ち上げる。起動と指示は `scripts/worker-shell.el` を使う。互いに独立な単位は、できるだけ並行して進める。cargoでビルドやテストをするworkerは同時に2本までとする。
- workerへの指示には、単位、作業するworktree、`CARGO_TARGET_DIR`、読むもの、出口、結果を書くfileを明記する。統括は結果のfileを読む。
- 各waveは、§3のどの単位を閉じるかを名指しする。同じ系統で2 wave続けて単位が閉じなければ、その系統を止めて設計問題として作者へ返す。使用量の上限は停止条件としてだけ扱う。
- 完了は§3の単位で数える。旧計画の72要件は分母にしない。
- 試作の記録はbranchのcommitとテスト記録とする。fileの複製、manifestの照合、pinの読み戻しは、登録した科学取得に限る。
- 合否に使う計時は、1セルの試行で基準の10倍以内に入ることを確かめてから排他の時間枠を取る。
- 作者へ判断を求めるときは、推奨ごとに、採ると発生する作業、採らないと消える作業、数値の由来、後から変える費用を書く。
