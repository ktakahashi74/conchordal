# 時間構造DCCの実装計画改訂

作成日: 2026-09-11
状態: 2026-09-12にI/R/A再編を採用。実行単位と現在地の正本は[milestones.md](milestones.md)。最新の実装状態は同正本§5を参照。2026-09-13にI9を研究拡張へ移管。旧M0全体と最終受入は未完了。
追加: Scenario／Rhai APIとUI/UXの最小範囲を§5.1に登録。観測経路は部分実装済みで、生成操作と全体受入は未完了。

## 1. 変更の目的と対象

今後の数値モデルはRustで実装し、そのコードを実験・性能測定・本体で共有する。
Python参照を本番相当まで高速化してからRustへ再実装する工程をやめ、
実音の観測から認知結果の配送までを早く接続する。独立検証と最終的な認知・音楽的判定は維持する。

対象は[完成計画](../temporal-dcc-completion.md)の実装言語、着手条件、作業順序、記録方法と、
作者がscenarioを指定・試聴・調整するための最小API・状態表示・操作手順である。
[神経認知階層メモ](../../design-notes/dcc-neurocognitive-hierarchy.md)のP/M/Aと[モデル交換境界](model-replacement.md)を引き継ぐ。
2026-09-13の採用範囲では本体T1–T6・四接続とし、I9/I12e/T7/O16は研究拡張へ分離する。
対象機構と生成作用を先に選び、必要な記憶範囲を定める。Scenarioの巨視的構成とTwinの聴取応答を区別し、
終端を持たない継続運転も設計対象にする。[正本§1.1](milestones.md#11-採用スコープと認知機構の選定2026-09-13)が以下の旧全階層条件に優先する。
R/H/C、現在の参照数式・特徴・尺度・容量、既定offとair-gapを、この工程変更では変えない。
本案の採用だけで、M0・O項目・MR試験を完了へ変更しない。

2026-09-11の確認では、追加された研究コード群はPython 23ファイル・8,330行、
Pythonテスト18ファイル・7,905行、独立Rust照合器1ファイル・1,150行である。
これはコメント等を含む物理行数であり、全行の移植が必要という見積りではない。
この時点では`src/temporal_cognition.rs`は存在しなかった。2026-09-12にM0数値準備として追加し、runtime接続前はcrateのtest buildから呼ぶ。
[M0台帳](m0.md)と[feasibility-preflight.json](feasibility-preflight.json)では、
全同時負荷は未検査、[feature-manifest.json](feature-manifest.json)も適合準備未完了である。

## 2. 現行工程からの変更

| 現行の進め方 | 修正案 | 品質と実装量への効果 |
|---|---|---|
| Pythonで数値・配送・所有・実時間性を作り込み、後にRustへ接続する | Rustを今後の実装正本とする。実験と本体は同じ関数・状態遷移を呼ぶ | 移植、二重保守、Python専用の高速化を減らし、本体の所有・期限の欠陥を早期に検出する |
| 初期実装と全研究準備をM0に束ねる | Iの動作完了とR/Aの研究・受入を分ける。旧M0は要求参照として保持する | 全モデルの実装準備をプロトタイプ側へ前倒しする負担を減らす |
| 参照実装の内部形式を配送経路へ持ち込む | モデル固有の表現を内部に閉じ、共通経路は意味・時刻・所有を扱う | モデル交換と不整合拒否を同じ本体経路で検査できる |
| 作者用APIの具体化を主にM8で行い、GUI・制作手順の受入条件は定めていない | W0で操作の意味と使用例を定め、M1から状態表示、M6から成立した生成操作を接続し、M8で最終整理する | 設定の意味と実際の作用のずれを早期に検出する。実装するUIの範囲を限定する |
| 工程計画・設計メモ・日英technoteへ実験経過を重複転記する | 各文書の責務を分け、詳細結果は一つの実験記録へ保存する | 更新漏れと長い再読を減らし、過去の証拠と現行状態を識別しやすくする |

### Pythonと既存成果の扱い

- 検証済みのPython参照・入力・期待出力・失敗例・回収結果は、対応するsource hashとともに保存する。
  現在の作業ツリーと最後の検証済み版を分け、進行中のpacked scheduler／worker変更を昇格させない。
- Pythonには、統計・適合・回収実験・作図・結果集計と、小型の独立参照を残す。
  純粋な仮説探索はPythonでもよいが、実時間workerや本体状態の第二実装へ育てない。
- `temporal_matcher_kernel.rs`の数値算法を再利用する。CPython API、ctypesの配置検査、
  GIL管理、Python辞書の展開を本体へ移植しない。既存の橋渡しコードは比較資料として残す。
- Pythonの任意の型や例外発生順序の再現はRust本体の要件にしない。
  不正値の拒否、欠測、原時刻、世代、未知と既知ゼロの区別は意味上の契約として維持する。
- 元のf64計算・u64識別子を維持して移す。加算順序・丸め・正規化の違いを単なる言語差として流さない。
  同値性を保てない変更は理由・許容誤差を先に登録し、影響する判定をやり直す。
  f32化、候補削減、容量変更は、必要性を実測した後の別の変更とする。
- 既存テストを行単位でRustへ翻訳しない。数式、独立列挙、因果反例、配送・所有の契約を選び、
  重複するPython型／ABI検査は旧参照側へ残す。未移管の検証範囲は明示する。

## 4. 必要な構造変更と再利用

最初は既存crate内部の`src/temporal_cognition.rs`を入口とし、実際の責務が生じた子moduleへ分ける。
公開API・別crate・汎用trait群を先に作らない。研究用テストはcrate内部から同じ実装を呼び、
継続的に別processから使う必要が生じた時点で、オフラインの小さい入出力driverを設ける。
適合・replay用driverが状態更新を再実装することは避ける。

| 境界 | 最初に触る既存箇所 | 変更と検査の範囲 |
|---|---|---|
| 数値算法 | [Rust照合器](../../../scripts/temporal_matcher_kernel.rs) | Python非依存の処理を安全なRustの参照・slice・所有へ移す。既存の算法と小型独立参照を照合する |
| 実音の証拠 | [analysis worker](../../../src/core/analysis_worker.rs)、[AnalysisStream](../../../src/core/stream/analysis.rs) | 最新Landscapeへ集約される前に順序付き証拠を渡す。既存NSGTを共有し、support・available時刻・epoch・gapを保持する |
| 配送と状態 | [runtime](../../../src/runtime/mod.rs)の`wire_runtime`・`WorkerState`・`process_hop` | 有界入力・一所有者の更新・期限付き結果を接続。habitat／presentationの状態は別。満杯・切断・退役時も欠落を隠さず、音声callbackを待たせない |
| 消費者 | [ListenerTwin](../../../src/listener_twin/mod.rs)、後に[参加処理](../../../src/life/temporal_participation.rs) | 由来付き要約を消費し、DTW・beam・codecへ依存しない。reportの有無で認知更新を変えない |

既存の`wire_runtime`によるGUI／headless／分離rendererの共通配線と、`process_hop`の分割を使う。
ファイルが長いという理由だけの`runtime`、`Community`、`Voice`全面再構成は先行させない。
変更が必要な責務を抽出し、機械的な移動と挙動変更を判別できる差分にする。
共有所有や固定poolの選択は実際の寿命・コピー・負荷で決め、Pythonのbyte poolを無条件に複製しない。
格納形式を変更した場合は版を分け、元の意味・容量制約を保った上で物理メモリ・コピーを再測定する。

### 5.1 Scenario／Rhai APIとUI/UXの最小範囲

作者の基本手順は「scenarioで指定→演奏→聴取と状態確認→編集して再実行」とする。
[現行の演奏手順](../../rhai_book_ja/src/tutorial/observing.md)を基礎に、設定と作用が対応しているかを
確認できる範囲を加える。初版GUIは状態確認を中心とし、設定の正本をGUIとscenarioに二重化しない。
新しいGUIエディタ、ライブ操作卓、長曲全体の可視化は本案の最小範囲に含めない。

#### APIの意味・対象・変更時点

| 層 | 作者が指定する内容 | 対象と変更の扱い |
|---|---|---|
| 身体・発音方針 | 同期、固有ペースでの参加、不規則な発音、持続と音長 | 既存PopulationSpecの`metric()`／`entrained()`／`flow()`等を基礎にする。新しい文脈設定だけで身体の意味を変更しない |
| 新しい時間認知の使用 | 既存動作、観測のみ、生成に反映の三mode | 演奏全体の開始前設定。時刻付き更新へ変換しない。演奏途中のmode変更は状態を変えず拒否し、別modeは空の記憶から新しい演奏を始める |
| 文脈への応じ方 | 関係の支持／逸脱、継続／終止、重なり等に対する作者の選好 | PopulationSpecで初期dispositionを指定する。必要な時刻付き更新は既存Population更新の経路へ接続し、M6の実消費者で検証してから公開する。mode変更とは区別する |

新しいdispositionはメモ§9.6の列挙済み帰結の符号付きgainで表し、追加の行動class事前値を作らない。
listener由来のgainは別扱いで初期値ゼロとする。研究用のbeam・検出閾値・fit係数を音楽的な操作へ偽装しない。
発声の保持時間を作者が設定する操作と、音から推定されるフレーズ長を区別する。
`section()`は作者の構成とreport用の印であり、認知が推定したsectionへ読み替えない。

現行`entrainment`はmetricで同期強度、entrained／flowで文脈の影響を表す。
この名前へ新しい長期文脈の作用まで追加せず、追加APIの意味を分離する。
既存の短期参加と新しい私有traceの適用関係はO19どおりに検査し、二重適用や暗黙の意味変更を避ける。
名称整理が必要なら対応表とsample差分を示し、無関係なAPIの一括改名や互換alias群を先行させない。

W0では、既存の最小scenarioにmodeとdispositionを加える構文案を作り、次を記載する。
設定の所有者、単位・範囲・既定、適用対象、宣言場所と適用時刻、重複／競合時の扱い、
Rhai／configの解決順序、無効値・未実装／未校正の作用に対するエラーまたは無効理由である。
scriptのcompile中に呼ばれた時刻付きmode設定を、開始前設定として黙って採用しない。
dispositionの時刻付き更新は明示された時刻以後の候補評価へ反映し、過去の観測や発行済み予測を改変しない。
実行できない構文案はその旨を明記し、実装後に実行可能な最小sampleへ置き換える。
APIの使い方を初めて考える時期はW0、正確な識別子・公開範囲・説明の最終固定はM8とする。

#### GUIとGUIなしの状態確認

新機能のoffは、従来の時間的動作まで無効にする意味ではない。表示名称は次の対応を基準にする。

| 内部のmodeの意味 | 表示の案 | 説明 |
|---|---|---|
| off | 既存動作 | 新しい時間文脈は使わず、従来の身体・参加処理で演奏する |
| passive observation | 観測のみ | 新しい関係を観測・保持するが、その行動列は生成に適用しない |
| local participation | 生成に反映 | 支持・鮮度・合法性等を満たす帰結だけを局所判断へ使う。設定だけで全作用が有効になるわけではない |

M1では小さい状態表示を作る。初期経路の未実装部分を、完成したmodeとして表示しない。

- **設定**: 解決済みmodeを表示し、Populationごとの設定は診断から確認できるようにする。設定名と有効な作用を区別する。
- **観測**: 未開始、待機、受信、欠落、遅延を実際の配送状態から示す。時刻・支持区間・epochを診断で確認できるようにする。
- **関係**: 未確定・候補・支持ありを、既存の証拠／不確かさの規約へ対応づける。UI専用の認知判定器や閾値を作らない。
- **作用**: 設定による無効、支持不足、未校正、期限切れ、適用可能を区別する。理由は実際の判定から取得し、画面側で推測しない。

無効理由は必要な帰結ごとに確認できるようにする。一部の未校正を全行動の停止として表示せず、
支持のある他の帰結や既存の身体動作と区別する。適用可能と、実際に選択・実行された行動も同一視しない。
不明をゼロの確信度や悪い音楽として見せず、同期度を音楽性の総合点にしない。
「Neural Rhythm」等の現行名称は、実際に推定している拍・同期等の内容に合わせて見直す。
作者が指定した区切りと推定された境界、生息環境の音と出力側の解析を表示上も区別する。

表示とreportは計算済みの共通要約を読む。`UiFrame`等の表示契約に必要な項目を渡し、
UIを開く、閉じる、更新を間引く操作で認知状態や音を変えない。GUIなしでも同じ診断を取得できる。
表示用snapshotの時刻と受信時刻を区別し、遅れて届いた表示を現在の支持として扱わない。
追加snapshot・文字列・転送の費用はO04/O17へ含める。全beamや全記憶を毎frameコピーしない。

#### 試聴・調整の手順

1. 最初に比較する問いを一つ決める。持続／release、先行文脈による終わり方等を選び、
   同時に音色・個体数・和声方針まで変更しない。提示音量の扱いも比較前に決め、元音源を保持する。
2. A/Bは別の演奏として実行し、条件・source・model・seed・素材と、意図した変更を記録する。
   同じseedだけでは入力・記憶・候補まで一致しない。探索的な別run比較と、O15の入力・履歴・身体・候補を
   揃えた状態介入を区別し、前者だけで因果効果を主張しない。
3. 保存する比較音源は`conchordal-render`から作る。楽器へ録音・巻き戻し・liveのmode切替を追加しない。
   フレーズ・帰還・全曲の比較では必要な先行部分も聴き、末尾だけの切り出しを同じ課題の代用にしない。
4. 聴取時のA/B表示はモデル名や望ましい答えを伏せ、「同じ」「判別できない」も正規の回答として残す。
   設定・診断の確認と聴取回答の順序を決め、診断表示だけから音楽的な成功を判定しない。
5. 結果と無効理由を確認してscenarioを編集し、新しい演奏を始める。作者の制作上の試聴は、
   O06/O08の独立聴取課題やT1–T7の他の判定を代替しない。

専用の拍打ちは同期が必須の比較・実演に限る。標準sampleはseed固定なし、研究assayはseed固定を維持する。
最初は既存renderer・再生手段と短い手順書を使い、新しい比較用アプリやプレイヤーの開発を前提にしない。

#### 工程別の成果物と受入

| W0／O21 | 三層の操作仕様、最小scenario構文案、設定・表示・試聴の対応表 | 適用対象・変更時点・エラー時の振る舞いが埋まり、未実装の構文と実行可能なAPIが識別できる |
| M1／O09・O21 | mode・観測・作用状態の表示と共通診断 | 未開始・欠落・遅延・旧epoch等のfixtureで表示理由と内部状態が一致する。GUI／reportの有無で認知と生成が変わらない |

Rhai APIの正本は`src/scripting/engine.rs`の登録と`src/scripting/docs.rs`である。

### 5.2 採用した身体アフォーダンスと認知機能の対応（2026-09-12）

アーティキュレーションは、身体に根ざしたgestureの生成と、その聴覚的な知覚・予測として扱う。
[設計メモ§3.1](../../design-notes/dcc-neurocognitive-hierarchy.md#31-adopted-circuit-and-embodied-affordance-interpretation-2026-09-12)の脳回路・認知機能・設計上の対応を採用する。
身体力学、感覚運動的な予測、音楽的文脈の三者を接続し、固有ペース・持続・回復・切替の制約を
認知側の期待から区別する。期待された境界が身体制約を迂回して即時releaseを命じる構造にはしない。
アフォーダンスは身体と音環境の関係であり、質量や固有振動数だけの属性ではない。

| 工程上の位置 | 追加する仕様・検査 |
|---|---|
| W0／M0のO02・O03・O06 | 身体設定、推定された認知量、工学上の制約を区別する。身体介入・文脈介入・交互作用の比較を登録し、Manifestoの身体意図と現行文面の明示範囲の差を技術ノートへ残す |
| W4／M2–M5 | 聞こえるgestureと身体による生成可能性を混同しない。まず既存の身体設定で比較し、質量・剛性等の物理モデルを追加する場合は法則・単位・根拠・再適合範囲を別途定める |
| W5／M6–M7のO15 | 身体状態、実行可能な候補、予測した帰結、実行結果を追跡する。同じ音・文脈で身体だけを変える比較、同じ身体・局所音で先行文脈を変える比較と、その交互作用を検査する |
| M9／O20 | T1とアーティキュレーション↔フレーズ接続の聴取判定へ対応させ、数値成立・認知対応・可聴性・作者採用を分ける |

この採用は設計方針と検証要件の採用である。新しい物理モデル、参照式・fit・feature版の変更、
実装完了、神経的妥当性、生成音の作者採用は意味しない。既存の工程修正案全体の採否とも区別する。
比較の詳細と交絡の扱いは設計メモ§10.2.1を参照する。

## 6. 品質を落とさずに検証とトークンを減らす方法

### 残す検証と早期の停止条件

数値実装、認知課題、可聴性、作者採用は別々に判定する。Rustへの移行が直接改善するのは、
実験結果の本体への適用性と、所有・配送・実時間の検査時期である。音楽性は従来の課題で判定する。

- **独立性**: 小型全列挙・手計算・解析式と既存Python参照を使う。本体関数を呼んで生成した期待値だけにしない。
- **因果・所有**: 未来の支持、旧epoch／世代、遅延、改訂、二重受領、queue飽和、drop・終了後の所有を検査する。
  off／受動で新しい行動圧力が出た場合や、ラベル・私有状態の漏洩があれば、その経路で止める。
- **資源**: releaseで、入力生成・コピー・queue待ち・計算・消費を識別して測る。
  部品のp99を足して全体のp99とせず、O04/O17の条件で全体を実測する。容量削減で検査を通さない。
- **統計**: 変更出力に依存するOOF入力・fit・校正を再生成し、再利用する枝には根拠を記録する。
  既存の回収成功を新しい実音尺度や身体へ自動転用しない。
- **手戻りの制限**: 一つの経路で予算を超えたら、その実装をprofileし、原因と次の比較を一つ定める。
  Python側の同等経路を新設して測り直す工程へ戻らない。模式入力の成功だけで下流の採用へ進めない。

各作業では変更に対応する検査を先に行い、成果物を閉じる時点でリポジトリ必須のRust検査を行う。
`src/`変更時の全文Cargo testログ・同一shellでの終了状態記録、fmt・clippy・all-targets確認は省略しない。
通過後に追加変更や未解決の疑義がなければ、同じ全検査を理由なく繰り返さない。
Python側を変更しない作業では、関連する固定参照の比較を使い、無関係なPython全体検査を増やさない。

### 記録と再開

| 記録 | 採用後に置く内容 |
|---|---|
| 設計メモ | 認知的意味・式・不変条件・根拠と限界。性能改善の実行経過はリンクにする |
| 完成計画 | 工程、依存、終了条件、O-ID対応。過去の最適化ログを追記しない |
| M0等の段階台帳 | 現在の状態・未達・次の一単位と証拠へのリンク。結果全文を複製しない |
| 実験記録 | 固定source・入力・コマンド・出力・判定・資源測定を一か所へ保存。失敗と旧版も保持する |
| 日英technote | Manifestoとの対応、方式・実装状況・新しい第一原理上の知見。細かなtimingの履歴は参照へ移す |

既存の長い記録は削除せず保存し、採用後の更新からこの運用へ移る。
文書版と数式・特徴・適合・保存形式の版を識別する。アーキテクチャの説明変更だけで実験を再実行せず、
過去の結果を新sourceへ付け替えない。複数台帳への現行hash反映は、一つの更新処理と整合検査で扱う。
各実装単位の開始時に読むのは、短い現在の台帳、対象仕様、対象コード、対応fixtureを中心とする。
新しい依存や矛盾を発見した場合にだけ関連資料へ広げる。

削減率・残りトークン数は未計測であり、本案では数値を約束しない。
W1–W2では、追加／削除コード量、維持する参照の数、修正往復、実行時間と、取得可能な使用量を記録する。
トークンが取得できる場合は入力・キャッシュ入力・出力を区別し、取得できなければ未計測とする。
終了条件を通した単位の費用を使って残作業を再見積りし、人の回答待ちや全曲試聴時間は別枠にする。
削減が確認できない場合は、重複している実装・記録を見直す。検証基準を下げて削減率を作らない。
§5.1で追加したAPI使用仕様、状態表示、試聴手順、文書の費用は別に積算する。
既存のmode隔離・診断・文書同期との重複を除き、残る追加費用を修正案の残作業へ加える。
会話で示した約1〜3割の削減試算は、このUI/UX追加を積算した値ではない。
